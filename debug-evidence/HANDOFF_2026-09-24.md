# Handoff: bench pump <> AAPS comms reliability investigation

**Goal (standing, from /goal):** make pump <> AAPS comms work reliably on the bench
pump (serial 646910), freely flash firmware and restart AAPS as needed.

**Status as of 2026-09-25 morning: STILL NOT FULLY RELIABLE, but real progress.**
The channel-bandwidth narrowing (see "2026-09-25 update" section near the
bottom) measurably speeds up and cleans the *initial* connect (PumpConnectorReady
+ valid PumpModel within ~30s of an AAPS restart, faster/cleaner than most of
the prior session's cycles), but follow-up commands (isDeviceReachable health
checks, GetRealTimeClock, etc.) are still intermittent after that. Only ~2
minutes of post-fix data has been collected — not enough to call this solved,
but it's the most promising single change of the whole investigation so far.
This doc is being updated live as the investigation continues — check the
"2026-09-25 update" section at the bottom for the most current findings before
anything above it, which reflects 2026-09-24's state.

## Physical setup
- Bench pump is **less than a foot away** from the board. Physical

- Non-prod Android test phone (Samsung SM-X520) runs the patched AAPS build,

## What's been tried and ruled out this session (chronological)

1. **Re-arm interval experiment (`SL_SUBG_RX_REARM_MS`)**: raised from 300ms
   to 5000ms on the theory that periodic re-arm dead zones were the dominant
   cause of missed catches. **Result: made things worse (0/5 automatic
   wakeUp successes vs baseline's prior demonstrated successes). Reverted to
   300ms.** Dead-zone-duration theory is refuted.

2. **RX frequency-sweep-offset fix, first version (reverted)**: hardcoded the
   first re-arm of every `sl_subg_get_pkt()` call to sweep offset 0 (nominal
   frequency), reasoning that 646910's replies were always seen at offset 0
   in earlier HackRF captures. **User correctly pointed out this was
   overfit** — HackRF ground-truth captures use a fixed wideband center
   frequency independent of our own re-arm/offset state, so they don't
   actually tell you which of *our* sweep offsets is correct. Any pump can
   be at any offset (560793 already needed +15-20kHz). Reverted.

3. **RX frequency-sweep-offset fix, adaptive version (currently in the
   firmware, KEPT)**: added `s_rx_last_good_offset_hz`, a persistent static
   that remembers the offset of the most recent successful reception and
   tries that first on every subsequent call's first re-arm, falling back to
   the normal persistent sweep index for re-arms after the first. This is
   correctly reasoned (adapts to whatever pump/crystal is actually in play)
   and empirically DOES work mechanically — produced 4 consecutive clean
   single-re-arm successful captures of a `GetPumpModel` reply in one
   window. **But it has not resolved overall reliability** — see aggregate
   counts below. Code: `src/drivers/rail/sl_subg_radio.c`, search
   `s_rx_last_good_offset_hz`.

4. **Aggregate hit-rate analysis via the firmware's own RAM ring-buffer log**
   (`dbg_log` — see `src/debug/dbg_log.c/h`, read via one-shot `commander
   readmem`, see "How to pull dbg_log" below): in one 16KB window sample,
   15/34 send-and-listen calls succeeded (44%), but critically:
   - **Every single successful call used exactly 1 re-arm** (immediate hit).
   - **Every single failed call exhausted its FULL re-arm budget** (83-84
     re-arms for a 25s wakeUp() call, cycling the whole sweep table multiple
     times) — total silence, not a near-miss.
   - This rules out frequency-offset/timing tuning as the remaining
     bottleneck: it's binary per-call (instant catch or total silence for
     the whole window), not "almost caught it."

5. **Isolated the dedicated 200-repeat `wakeUp()` call specifically** (the
   `listen 25000 ms` calls in dbg_log, called from AAPS's
   `RileyLinkCommunicationManager.wakeUp()`): **0/15 successes** in the
   sampled window. ALL 15 dbg_log successes were instead `listen 1250 ms`
   calls — AAPS's `scanForDevice()` per-candidate-frequency probes, a
   different code path entirely.

6. **Correlated tuned frequency against outcome** (grep `tuned to` vs `RX
   call summary` in dbg_log): revealed ALL successes clustered at
   916.749755 Hz / 916.799926 Hz, and ALL failures clustered at
   916.599975 Hz — suggesting (at first) a stale/wrong frequency being used
   for wakeUp() specifically.

7. **Pulled AAPS's own `scanForDevice()` "Scan results:" log lines directly**
   (search `Scan Result\[` in AndroidAPS.log): TWO separate scans minutes
   apart both showed **strong, consistent, real signal (-71 to -85 dBm) at
   916.500-916.600 MHz**, and a suspicious *uniform* -128.0 dBm (identical
   across every try) at 916.65-916.80 MHz. Traced `radioResponse.rssi`
   (AAPS/Kotlin side, `RadioResponse.kt:67`) — confirmed it's literally our
   own firmware's self-reported RSSI byte from the `[0xDD][rssi][pktCnt]`
   response header (`aps.c` `respond_rx_packet()`), NOT anything
   pump-embedded. The uniform -128.0 at .65-.80 is consistent with a
   genuine (if weak, ~-110 dBm) noise-floor capture that passed our CRC by
   chance, not the real pump. **This means 916.500-916.600 is very likely
   the pump's actual, stable frequency** — which contradicts point 6 above.
   This contradiction is not yet resolved (see next steps).

8. **Traced `CMD_UPDATE_REG` (frequency-set registers 0x09/0x0A/0x0B)**:
   confirmed this runs **inline, never queued** (`aps.c` `aps_put_cmd()`,
   search "CMD_UPDATE_REG runs inline"), so it cannot race behind the
   command queue. The specific "CMD_UPDATE_REG addr 0x0f/0x10/0x11 ignored"
   lines seen interleaved with queue congestion are NOT frequency registers
   at all — unrelated/unimplemented registers being harmlessly ignored.
   Ruled out as an explanation for stale-frequency wake failures.

9. **Live HackRF capture directly correlated with a triggered wakeUp()
   attempt** (`debug-evidence/captures/bench_646910_single_wake_correlate_20260924.cs8`,
   40s, HackRF centered at 916.600 MHz, triggered via
   `adb shell am broadcast -a AAPS.RileyLink.MSG_PUMP_tunePump` at wall-clock
   20:25:32, capture Birth timestamp 20:25:25.714 = t=0):
   - `decode_ook_serials.py` found 0 CRC-valid frames, BUT this is a false
     negative: **the tool assumes a fixed +500kHz demod offset calibrated
     for a 916.5 MHz capture center** (see `OFFSET = 500_000.0` in
     `tools/decode_ook_serials.py`). This capture used 916.6 MHz center, so
     the tool was looking 100kHz away from where it needed to.
   - Wrote a standalone FFT-based burst-frequency finder
     (`/tmp/.../scratchpad/find_burst_freqs.py` — **not yet copied into the
     repo, do that if it proves useful**) that measures each burst's actual
     carrier frequency independent of the decoder's fixed-offset assumption.
   - Result: found a tight cluster of TX bursts (200-repeat wake pattern,
     ~191-392ms bursts every ~200ms) all within ~60 Hz of **916.57893 MHz**
     — very stable, almost certainly our own bridge's TX. Two clusters seen:
     one right at capture start (t=0-0.83s, tail of an already-in-progress
     wake), then a ~25 second silent gap (matching the 25000ms listen
     window), then a fresh wake burst cluster from t=25.9s to t=29.2s.
   - **One final, different burst at t=29.2866s: 62ms duration (matches a
     real 71-byte Minimed reply's on-air time), at 916.69884 MHz** — about
     120 kHz higher than our own TX frequency, and also notably different
     from the 916.6 MHz AAPS believes it configured.
   - **This result was NOT yet sanity-checked before this doc was written**
     — was about to re-run the same FFT method against an earlier capture
     with known-good `decode_ook_serials.py` successes
     (`bench_646910_scan_final_responsecnt_20260924.cs8`) to confirm the FFT
     peak-frequency method itself is trustworthy (OOK/ASK modulation has
     spectral content beyond a single clean tone, so a naive FFT peak could
     be misleading) before treating the 916.579 vs 916.699 MHz gap as real.
     **Do this sanity check first if picking this up.**

## Update: FFT method validated, but the "TX miscalibration" theory has a
## serious unresolved confound — READ THIS BEFORE TRUSTING THE FREQUENCY-GAP FINDING

The FFT burst-frequency method (`find_burst_freqs.py`) WAS sanity-checked
against a known-good capture (`bench_646910_scan_final_responsecnt_20260924.cs8`,
burst at t=8.4847s, known to decode successfully as our own wake TX
`a76469108d00b3`) and measured 916.57969 MHz — within ~1 kHz of the same
measurement in the new capture (916.578-916.579 MHz). The method itself is
reliable and reproducible.

Bit-level decode debugging (`debug_decode.py`) on the new capture's bursts
found the sync word correctly and started decoding the same way as the
known-good capture (`a969b4999c5568d5...` matches at the start) before
diverging into garbage a few bytes in — this looks like a demod-quality/gain
artifact between captures (different `-g`/`-l` gain settings used), NOT a
frequency problem. Also found: the one differently-tuned burst at
t=29.2866s (916.69884 MHz, 62ms — matching a real 71-byte reply's on-air
time) decoded its first byte as `0xA7`, the exact Minimed serial-marker byte
every valid frame in this investigation starts with — strong evidence it's
a genuine pump transmission, not noise.

**However — do not conclude "our TX is miscalibrated by ~21kHz" from this.**
Checked `freq_from_regs()` in `aps.c`: `APS_RILEYLINK_FXOSC = 24000000ULL`,
the correct, standard CC1110/RileyLink crystal reference constant — not a
plausible source of a software conversion bug. The real remaining confound:
**the HackRF One used for all these captures has no verified frequency
calibration.** Stock HackRF crystal tolerance is commonly ±20ppm, which at
916 MHz is ~18kHz of *purely spurious* apparent frequency error — a
magnitude fully capable of producing the ~21kHz gap measured here on its
own, with zero real miscalibration on our board. **The "our TX lands 21kHz
away from commanded" and "pump reply lands 120kHz from our TX" findings are
therefore NOT solid** until the HackRF itself is calibrated (e.g. `hackrf_debug`
PPM correction against a known reference, or cross-checking against a signal
of independently-known frequency) or the measurement is corroborated by a
DIFFERENT method that doesn't depend on the HackRF's own oscillator.

**More trustworthy than any HackRF measurement**: AAPS's own `scanForDevice()`
"Scan results" (point 7 above) are measured using OUR OWN BOARD's radio
in-situ, with no external device/calibration dependency — and that data says
916.500-916.600 MHz genuinely has real signal (-71 to -85 dBm, strong and
consistent across two separate scans). This is NOT actually contradicted by
anything solid — the frequency-gap theory above should be considered
UNCONFIRMED, likely a HackRF measurement artifact, and deprioritized unless
recalibrated measurements say otherwise.

## Current best-supported theory: it's a numbers game, not a frequency problem

Setting the frequency-gap theory aside, the pattern that DOES hold up under
scrutiny: **`scanForDevice()` succeeds because it makes ~24 independent short
attempts** (8 candidate frequencies x 3 tries, each a full
transmit-then-listen exchange, ~1250ms each) even though it only calls
`wakeUp()`'s big 200-repeat burst ONCE at the very start. **A standalone
`isDeviceReachable()`/`wakeUp()` call gets, functionally, ONE overall
opportunity** — 200 TX repeats improve the odds the pump *hears* the wake,
but the actual reply is still just one exchange to catch in the one 25s
listen window that follows. If the true per-exchange success probability is
genuinely well under 100% (consistent with the ~44% aggregate hit rate
measured in dbg_log across all call types), then MANY independent short
attempts (scanForDevice's approach) will statistically outperform ONE
long attempt (wakeUp's approach), regardless of frequency.

**This points at an actionable, concrete fix in AAPS/Kotlin, not firmware**:
restructure `RileyLinkCommunicationManager.wakeUp()` (or
`MedtronicCommunicationManager.isDeviceReachable()`'s retry loop) to issue
several independent shorter transmit-then-listen attempts instead of one
big 200-repeat/25000ms attempt — mirroring what `scanForDevice()` already
does successfully, without needing multiple frequencies (since the real
frequency is presumably already known/correct once tuned). NOT YET TRIED —
this is the next concrete thing to test, pending user input (this was being
discussed with the user via chat when this doc was last updated; check the
conversation, or ask, before assuming go-ahead to modify AAPS Kotlin sources
further — several other AAPS patches this session were applied only after
explicit user authorization).

## How to reproduce / pull diagnostics

- **dbg_log (firmware RAM ring buffer)**: independent of any live debug
  session, survives RTT disconnects. Get current symbol addresses (they
  shift slightly between builds):
  ```
  NM=/home/charles/.silabs/slt/installs/conan/p/gcc-a469753773d4f2/p/bin/arm-none-eabi-nm
  "$NM" /home/charles/SimplicityStudio/v6_workspace/orangelink_xg28/cmake_gcc/build/base/orangelink_xg28.out \
    | grep -E "s_dbg_log_total_written|s_dbg_log_buf\b"
  ```
  Then one-shot read + reconstruct (handles wraparound):
  ```
  CMD=/home/charles/.silabs/slt/installs/archive/commander/commander
  "$CMD" readmem --range <total_written_addr>:+4 -o total_written.bin -d EFR32ZG28B312F1024IM48
  "$CMD" readmem --range <buf_addr>:+16384 -o buf.bin -d EFR32ZG28B312F1024IM48
  python3 -c "
  import struct
  with open('total_written.bin','rb') as f: total_written = struct.unpack('<I', f.read(4))[0]
  with open('buf.bin','rb') as f: buf = f.read()
  buf_size = len(buf)
  start = total_written % buf_size if total_written > buf_size else 0
  data = (buf[start:] + buf[:start]) if total_written > buf_size else buf[:total_written]
  open('reconstructed.txt','wb').write(data)
  "
  ```

- **commander / arm-none-eabi-nm are NOT on PATH** in this shell — use full
  paths:
  - `commander`: `/home/charles/.silabs/slt/installs/archive/commander/commander`
  - `arm-none-eabi-nm`: `/home/charles/.silabs/slt/installs/conan/p/gcc-a469753773d4f2/p/bin/arm-none-eabi-nm`

  ```
  cp src/<file> /home/charles/SimplicityStudio/v6_workspace/orangelink_xg28/<same relative path minus src/>
  cd /home/charles/SimplicityStudio/v6_workspace/orangelink_xg28/cmake_gcc/build && ninja
  ```

  AAPS.RileyLink.MSG_PUMP_tunePump`

  /storage/emulated/0/Android/data/info.nightscout.androidaps/files/AndroidAPS.log

  re-pull periodically.

  tools/decode_ook_serials.py <file>.cs8 --serial 646910`. Use `stat

## 2026-09-25 update: found and fixed a real cross-pump-interference bug

**New theory (user's insight, now acted on):** stock RileyLink/OrangeLink
hardware doesn't have trouble with multiple nearby Medtronic pumps; this
board does. The likely cause: this session (2026-09-24) had *widened* the RX
channel filter from 118560 Hz to 191840 Hz (raising `rx_xtal_error_ppm`/
`tx_xtal_error_ppm` from 10 to 30) to tolerate individual-pump crystal drift.
That wider passband, combined with a receiver sensitive enough to hear a
different pump at range (the AAPS-side scan showed strong real signal, and
partial captures in the logs decoded to serial `560793` — the user's *real*
production pump, picked up incidentally, not something we transmitted to —
see the existing safety note on 560793 elsewhere in this project), was
plausibly wasting listen-window catches on the wrong pump's traffic. Since
the adaptive-offset fix (`s_rx_last_good_offset_hz`, kept from the prior day)
now handles per-pump drift by adapting rather than needing a wide filter, the
wide filter was doing more harm than good.

**Action taken:** reverted `rx_xtal_error_ppm`/`tx_xtal_error_ppm` back to
10 via the Radio Configurator GUI (no CLI path exists for this — confirmed
via docs.silabs.com that Simplicity Studio's own Radio Configurator is the
only way, and even there, do NOT hand-type a value into "Acquisition
Channel Bandwidth" or "IF Frequency" — leave those unchecked/auto and let
the tool compute them correctly on save). Verified via the correct formula,
found in the field's own tooltip and cross-validated exactly against two
historical data points from this project:
`BW_Hz = 5 × bitrate_bps + 2 × center_freq_Hz × (tx_ppm + rx_ppm) × 1e-6`
- 10/10 ppm → 118560 Hz (confirmed exact match after regeneration)
- 30/30 ppm → 191840 Hz (matches the prior day's measured value)

**A real gotcha hit along the way, now resolved — READ THIS IF A FUTURE
REGENERATION BREAKS THE BUILD AGAIN:** saving in the Radio Configurator
regenerated more than just `autogen/rail_config.c`/`.h` — it also fully
regenerated `cmake_gcc/orangelink_xg28.cmake` (the auto-generated CMake
project file, explicitly marked "Automatically-generated file. Do not
edit!"), and that regeneration **dropped every hand-added source file and
include path** from it: `aps/aps.c`, `aps/aps_transport.c`,
`drivers/rail/sl_subg_radio.c`, `debug/dbg_log.c`, `encoding/4b6b.c`,
`encoding/manchester.c`, plus the whole RTT/printf/iostream logging stack
(`segger_rtt`, `printf`, `iostream_*`, `cmsis_os2_ext_task_register`) and
even a legitimately-needed SDK component (`sl_rail_util_rf_path_switch`)
that was already correctly declared in `.slcp` but not wired into the
generated CMake file either. This was a broad, one-off generator glitch, not
specific to the radio change — **all the custom sources are correctly and
persistently declared in `orangelink_xg28.slcp`'s own `source:`/`include:`
blocks**, which is the actual source of truth and was never at risk; the bug
was purely in the .slcp → .cmake generation step for this one save. Fixed by
manually re-adding the missing `target_include_directories` entries and
`add_library(slc OBJECT ...)` source entries to `orangelink_xg28.cmake`,
cross-checked file-by-file against what `.slcp` declares plus the newly
needed `sl_rail_util_rf_path_switch.c`/RTT stack SDK paths (found by
grepping the SDK tree for the exact missing header/symbol names — see git
history/this session's transcript for the exact list if this happens again).
Build succeeded and firmware flashed cleanly after this fix.
